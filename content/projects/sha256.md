Do not ship hand-rolled cryptography. Use the `sha2` crate, or `ring`, or
whatever your platform already links against, because those have constant-time
review, assembly paths for the SHA extensions your CPU almost certainly has, and
years of people trying to break them. If you are hashing passwords, SHA-256 is
the wrong primitive entirely and you want `argon2` or `bcrypt`. This project is
for understanding, and understanding is the only thing it is for.

With that said: SHA-256 is one of the most-run pieces of code on earth. Every
TLS certificate chain, every git object name, every Bitcoin block header goes
through it. And the whole algorithm is about sixty lines. It takes a message,
pads it to a multiple of 64 bytes, and then runs each 64-byte block through 64
rounds of shuffling eight 32-bit registers, mixing in one constant and one
derived word per round. There is no magic step. There is arithmetic, done
carefully.

Careful is what Rust is good at here. FIPS 180-4 is written in terms of
operations that are all distinct and all easy to confuse: rotate right against
shift right, addition modulo 2^32 against ordinary addition, big-endian byte
order against whatever your machine prefers. In C those are `>>`, `+` and a
comment. In Rust each one is a named method that means exactly one thing:
`rotate_right`, `wrapping_add`, `to_be_bytes`. Writing the wrong one is a
compile error or a debug panic rather than a wrong digest you discover in
production.

Four stages: the bit primitives, the padding, the compression function, and then
the three test vectors NIST publishes, asserted to the character.

## 1. The primitives, one method each

@kind fix
@concept operator

@expect E0599

Section 4.1.2 of FIPS 180-4 defines six functions on 32-bit words, built out of
rotate, shift, and, xor and not. Five of them are written. `big_sigma1` is
written the way the spec reads it, `ROTR^6(x)`, and Rust does not have that
method.

```starter
pub const W0: u32 = 0x6162_6380;

pub fn rotr(x: u32, n: u32) -> u32 { x.rotate_right(n) }
pub fn shr(x: u32, n: u32) -> u32 { x >> n }
pub fn ch(x: u32, y: u32, z: u32) -> u32 { (x & y) ^ (!x & z) }
pub fn maj(x: u32, y: u32, z: u32) -> u32 { (x & y) ^ (x & z) ^ (y & z) }
pub fn big_sigma0(x: u32) -> u32 { rotr(x, 2) ^ rotr(x, 13) ^ rotr(x, 22) }
pub fn big_sigma1(x: u32) -> u32 { x.rotr(6) ^ x.rotr(11) ^ x.rotr(25) }
pub fn small_sigma0(x: u32) -> u32 { rotr(x, 7) ^ rotr(x, 18) ^ shr(x, 3) }
pub fn small_sigma1(x: u32) -> u32 { rotr(x, 17) ^ rotr(x, 19) ^ shr(x, 10) }

pub fn run() -> [u32; 4] {
    let out = [big_sigma0(W0), big_sigma1(W0), small_sigma0(W0), small_sigma1(W0)];
    println!("w               = {W0:08x}");
    println!("big_sigma0(w)   = {:08x}", out[0]);
    println!("big_sigma1(w)   = {:08x}", out[1]);
    println!("small_sigma0(w) = {:08x}", out[2]);
    println!("small_sigma1(w) = {:08x}", out[3]);
    out
}
```

@hint `rotr` exists in this file. Look at how `big_sigma0` on the line above calls it.
@hint `rotr` is a free function, not a method on `u32`, so it is called as `rotr(x, 6)`.
@hint `rotr(x, 6) ^ rotr(x, 11) ^ rotr(x, 25)`.

@diagnose E0599
`no method named rotr found for type u32 in the current scope`.

A method call `x.rotr(6)` asks rustc to look for `rotr` in the inherent
implementations of `u32` and in every trait implemented for `u32` that is in
scope. Your `pub fn rotr(x: u32, n: u32)` is in neither. It is a plain function
at module level, and the only way to reach it is `rotr(x, 6)`.

The two forms are not interchangeable in Rust the way they are in some
languages. `impl u32 { fn rotr }` is not something you can write for a type you
do not own, so a free function is the right shape here. The real name for what
the spec calls ROTR is `u32::rotate_right`, which is why `rotr` is a one-line
wrapper: the spec's vocabulary, spelled the spec's way.

@diagnose E0308
Check the shift counts. All eight of these functions take and return `u32`, and
the rotate and shift amounts are `u32` too, so nothing here needs a cast. If you
introduced a `usize` or a signed literal, that is the mismatch.

@after
Six functions, and the whole difficulty is that they look alike. `big_sigma0`
and `small_sigma0` differ only in three numbers and in whether the last term
rotates or shifts. That last difference matters: the sigma functions used on the
message schedule end in a shift, so bits fall off the end and the schedule
cannot be run backwards word by word.

`ch` picks bit by bit, x chooses y where x is 1 and z where x is 0. `maj` is the
bitwise majority vote of three words. Both are cheap and both are non-linear,
which is the point. Xor and rotate alone would give an algorithm you could solve
with linear algebra.

## 2. Padding, and the block that does not fit

@kind fix
@concept integer

@expect E0308

The compression function eats exactly 64 bytes at a time, so the message has to
be stretched to a multiple of 64 first. The recipe from section 5.1.1: append a
single 1 bit (one `0x80` byte, since messages here are whole bytes), then zeros,
then the message length in bits as a 64-bit big-endian integer, sized so the
total lands on a block boundary. The length line will not compile.

```starter

pub fn rotr(x: u32, n: u32) -> u32 { x.rotate_right(n) }

pub const V3: &str = "abcdbcdecdefdefgefghfghighijhijkijkljklmklmnlmnomnopnopq";

pub fn pad(msg: &[u8]) -> Vec<u8> {
    let bits: u64 = msg.len() * 8;
    let mut out = msg.to_vec();
    out.push(0x80);
    while out.len() % 64 != 56 {
        out.push(0);
    }
    out.extend_from_slice(&bits.to_be_bytes());
    out
}

pub fn run() -> Vec<usize> {
    let long = "a".repeat(55);
    let mut lens = Vec::new();
    for msg in ["abc", "", &long, V3] {
        let padded = pad(msg.as_bytes());
        println!(
            "{:3} bytes -> {:3} padded, {} block(s), length field {:02x?}",
            msg.len(),
            padded.len(),
            padded.len() / 64,
            &padded[padded.len() - 8..]
        );
        lens.push(padded.len());
    }
    lens
}
```

@hint `msg.len()` is a `usize`. The binding says `u64`. Rust will not widen one into the other on its own.
@hint The cast has to happen before the multiplication, or the multiplication happens in `usize` and only then gets converted.
@hint `msg.len() as u64 * 8`.

@diagnose E0308
`expected u64, found usize`, with the annotation on the binding underlined as
`expected due to this`.

`Vec::len` returns `usize`, the width of a pointer on this machine. `u64` is
exactly 64 bits everywhere. On the 64-bit machine you are probably reading this
on they hold the same values, and Rust still refuses, because the two types are
distinct and the code has to say which one it means.

Here that pedantry is doing real work. The spec says the length field is 64 bits,
full stop. If you wrote `usize` and compiled for a 32-bit target, `to_be_bytes`
would produce four bytes instead of eight, the block would be short, and every
digest would be wrong. Writing `as u64` pins the width to what the standard
says rather than to the machine.

@diagnose E0277
Probably `bits.to_be_bytes()` handed straight to `push` rather than
`extend_from_slice`. `push` takes one `u8`; `to_be_bytes` gives `[u8; 8]`. Pass
a reference to the array and use `extend_from_slice`, which takes a slice of the
element type.

@after
The `!= 56` in the loop is the whole edge case. Zeros are appended until 56 bytes
into a block, leaving exactly 8 for the length. A 56-byte message has no room:
the `0x80` lands at offset 56, the loop cannot stop there, so it fills to 120 and
the message becomes two blocks. That is why the third NIST vector is 56 bytes
long. It exists specifically to catch implementations that assume one block.

The padding is also why SHA-256 is not vulnerable to trivial extension of the
kind `md5(secret || msg)` invites in some constructions: the length is part of
what gets hashed, so a message and a longer message with the same prefix pad
differently. Length extension against the raw compression function is still real,
which is why HMAC exists.

## 3. The schedule and the sixty-four rounds

@kind fix
@concept slice

@expect E0308

Now the core. Each 64-byte block becomes 64 words: the first sixteen are the
block read big-endian, and the rest are stirred out of earlier words with the
small sigmas. Then eight working registers go round 64 times, each round folding
in one constant from `K` and one word from the schedule. The line that reads
four bytes into a word does not compile.

```starter
pub fn schedule(block: &[u8]) -> [u32; 64] {
    let mut w = [0u32; 64];
    for t in 0..16 {
        w[t] = u32::from_be_bytes(&block[t * 4..t * 4 + 4]);
    }
    for t in 16..64 {
        w[t] = small_sigma1(w[t - 2])
            .wrapping_add(w[t - 7])
            .wrapping_add(small_sigma0(w[t - 15]))
            .wrapping_add(w[t - 16]);
    }
    w
}

pub fn compress(state: &mut [u32; 8], block: &[u8]) {
    let w = schedule(block);
    let [mut a, mut b, mut c, mut d, mut e, mut f, mut g, mut h] = *state;
    for t in 0..64 {
        let t1 = h
            .wrapping_add(big_sigma1(e))
            .wrapping_add(ch(e, f, g))
            .wrapping_add(K[t])
            .wrapping_add(w[t]);
        let t2 = big_sigma0(a).wrapping_add(maj(a, b, c));
        h = g;
        g = f;
        f = e;
        e = d.wrapping_add(t1);
        d = c;
        c = b;
        b = a;
        a = t1.wrapping_add(t2);
    }
    for (s, v) in state.iter_mut().zip([a, b, c, d, e, f, g, h]) {
        *s = s.wrapping_add(v);
    }
}

pub fn run() -> [u32; 8] {
    let mut state = H0;
    compress(&mut state, &pad(b"abc")[..64]);
    for (i, word) in state.iter().enumerate() {
        println!("H[{i}] = {word:08x}");
    }
    state
}
```

@hint `from_be_bytes` wants an array of exactly four bytes. A range index gives a slice, whose length the compiler does not know.
@hint `TryInto` converts a slice to a fixed-size array at runtime, returning a `Result` because the length might not match.
@hint `u32::from_be_bytes(block[t * 4..t * 4 + 4].try_into().unwrap())`.

@diagnose E0308
`expected [u8; 4], found &[u8]`, pointing at the argument.

`block[a..b]` is a slice. Its length lives in the value at runtime, so as far as
the type system is concerned it could be any length. `[u8; 4]` is four bytes and
the compiler knows it, which is exactly what `from_be_bytes` needs in order to
be a compile-time reinterpretation with no bounds check.

`try_into()` is the bridge between the two. It compares the lengths at runtime
and gives back a `Result`, and `unwrap` says you have already reasoned that the
range is four wide. This is the whole slice-versus-array distinction in one line,
and it is the reason Rust can hand you `from_be_bytes` with no error case of its
own.

@diagnose E0277
If you reached for `block[t * 4..t * 4 + 4].into()` rather than `try_into()`,
rustc will say `the trait From<&[u8]> is not implemented for [u8; 4]`. There is
no infallible conversion, because a slice of the wrong length has to fail
somehow. `TryFrom` is the version that admits it.

@after
Run it and the eight words print as `ba7816bf 8f01cfea ...`, which is the
published digest of `"abc"` before it has even been turned into bytes. One
block, and the answer is already there.

Every addition in that loop is `wrapping_add`. Written with `+`, the first block
of almost any input overflows a `u32` and a debug build panics with `attempt to
add with overflow`. That panic is a feature. The spec says addition modulo 2^32,
and in Rust modular addition has its own name, so an accidental overflow in code
that did not intend one still gets caught. C gives unsigned overflow the same
wrapping behaviour by default, which makes SHA-256 convenient and every other
piece of arithmetic slightly dangerous.

The constants are not arbitrary and not chosen by anybody's taste: `H0` is the
first 32 bits of the fractional parts of the square roots of the first eight
primes, and `K` the same for the cube roots of the first sixty-four. They are
nothing-up-my-sleeve numbers, published so that nobody has to trust that a
back door was not hidden in them.

## 4. The three published vectors

@kind fix
@concept slice

@expect E0277

Everything is in place. What is left is the loop over blocks, the eight state
words serialised big-endian into 32 bytes, and a hex printer. Then the three
test vectors from the NIST examples get asserted character by character:
`"abc"`, the empty string, and the 448-bit message that spills into a second
block. `hex` does not compile.

@hint A `&u8` is a number, not a character. Something has to turn each one into two hex digits first.
@hint `format!("{b:02x}")` produces a two-character `String` for one byte, zero padded.
@hint `digest.iter().map(|b| format!("{b:02x}")).collect()`.

@diagnose E0277
`a value of type String cannot be built from an iterator over elements of type
&u8`.

`collect` is chosen by the type it collects into, and `String` implements
`FromIterator` for `char`, for `&str`, for `String`, and for a couple of
relatives, but never for a byte. It cannot: the byte `0xba` is not a character,
it is a number that you want written as the two characters `b` and `a`, and only
you know that hex is the encoding you meant.

Note what the error is not. Rust is not guessing wrongly about your intent, it is
saying that the function you asked for does not exist. Map each byte to a
`String` of two hex digits and `collect` finds `FromIterator<String> for String`,
which concatenates.

@diagnose E0308
If you wrote `digest.iter().map(|b| format!("{b:02x}")).collect::<Vec<String>>()`
the elements are right and the container is wrong. Either drop the turbofish and
let the return type pick `String`, or finish with `.join("")`.

@after
Three digests, matching the values in the NIST examples exactly:

```text
ba7816bf8f01cfea414140de5dae2223b00361a396177a9cb410ff61f20015ad  "abc"
e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855  ""
248d6a61d20638b8e5c026930c3e6039a33ce45964ff2167f6ecedd419db06c1  "abcdbcdecdef..."
```

The second one is worth a look. Hashing nothing at all still runs a full block,
because padding an empty message produces 64 bytes of `0x80` and zeros, and
`e3b0c442...` is a constant you will start recognising in git and in Docker
layer digests once you know it.

What this is missing before it could be used for anything real: it is not
constant-time in any audited sense, it copies the message into a fresh `Vec` to
pad it rather than streaming, and it ignores the SHA extension instructions that
make `sha2` roughly ten times faster on a modern x86 or ARM core. It also has no
incremental API, so hashing a large file means holding the file in memory. Those
are the differences between a correct implementation and a usable one, and they
are the reason the advice at the top stands.
